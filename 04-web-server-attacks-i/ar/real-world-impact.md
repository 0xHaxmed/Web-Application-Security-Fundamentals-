## 🌐 1. أخطاء الإعداد الأمني في سوق العمل (OWASP A05:2021)

وفقاً لإحصائيات كبرى شركات الأمن السيبراني وتقارير **OWASP Top 10**، تمثل **أخطاء الإعداد الأمني (Security Misconfigurations - A05:2021) الفئة الأكثر تسجيلاً على الإطلاق في تقارير اختبار الاختراق الميدانية للشركات**؛ حيث تشكل وحدها ما بين 40% إلى 60% من إجمالي الثغرات المسجلة!

بينما يركز المبتدئون على البحث عن ثغرات معقدة ونادرة، يدرك مستشارو الأمن المحترفون أن **الإعدادات الافتراضية غير المحصنة، ولوحات التشخيص المنسية، وتسريبات السيرفرات المؤقتة هي البوابة الأسهل والأسرع لاختراق الشبكات الداخلية للشركات**.

### سيناريوهات واقعية من بيئات الإنتاج:

1. **كوارث لوحات المراقبة المكشوفة (`/server-status` و `/nginx_status`):**
   * *السيناريو:* توفر موديولات مثل `mod_status` في أباتشي لوحة لعرض عناوين IP للزوار، واستهلاك السيرفر، **والروابط الدقيقة التي يطلبها المستخدمون حالياً (Current URLs)**.
   * *الكارثة الأمنية:* إذا كان الموقع يمرر رموز إعادة تعيين كلمة المرور أو توكنات المصادقة في الرابط (مثل `/reset?token=xyz123`)، فإن هذه الرموز **تظهر بنص صريح على لوحة `/server-status` لأي مراقب خارجي**، مما يتيح سرقة حسابات المستخدمين فوراً ويوقع الشركة في مخالفة صريحة لقوانين الخصوصية العالمية مثل GDPR.

2. **فخ خادم بايثون "المؤقت":**
   * *السيناريو:* يحتاج مهندس الـ DevOps لنقل ملف مضغوط أو نسخة قاعدة بيانات سريعة بين سيرفرين في سحابة AWS، فيقوم بتشغيل:
     ```bash
     python3 -m http.server 8000
     ```
     ثم ينهي عمله ويغلق الشاشة، دون أن يدرك أن العملية ظلت تعمل في خلفية النظام (Background Process).
   * *الكارثة الأمنية:* محركات الفحص العالمية (مثل Shodan و Censys) أو المهاجمون يرصدون المنفذ المفتوح 8000، ويقومون بتحميل ملفات `.env` والمفاتيح السرية `id_rsa` والنسخ الاحتياطية دون مواجهة أي كلمة مرور!

3. **كسر ملفات `.htpasswd` المسربة دون اتصال (Offline Hash Cracking):**
   * *السيناريو:* يستخدم المطور نظام المصادقة الأساسي (Basic Auth) لحماية لوحة الإدارة في أباتشي، لكنه يضع ملف كلمات المرور `.htpasswd` داخل مجلد الموقع بدلاً من حفظه خارج جذر الويب.
   * *الكارثة الأمنية:* يتم تحميل الملف عبر أدوات التخمين مثل Gobuster، ثم كسر تجزئات كلمات المرور (Hashes) عبر كروت الشاشة باستخدام أداة Hashcat، وغالباً ما تكشف كلمات سر مدراء النظام الحقيقيين.

4. **اختطاف النقر وغياب الترويسات الدفاعية (Clickjacking - CWE-1021):**
   * *السيناريو:* موقع بنكي أو منصة تجارية لا ترسل ترويسات `X-Frame-Options` أو سياسة `Content-Security-Policy`.
   * *الكارثة الأمنية:* يضع المهاجم واجهة الموقع البنكي الحقيقية داخل إطار شفاف (`<iframe>`) فوق لعبة أو زر وهمي على موقعه الخبيث. عندما يضغط الضحية على الزر الظاهر، ينقر في الحقيقة على زر "تحويل الأموال" داخل حسابه البنكي المفتوح دون أن يدري!

## 📝 2. نموذج تقرير احترافي للعميل (Pentest Report Finding)

إليك الصياغة المعتمدة لتوثيق لوحة تشخيص أباتشي المكشوفة:

```markdown
### تقرير ثغرة: كشف نشاط وخوادم السيرفر عبر واجهة Apache mod_status العامة

* **مستوى الخطورة:** متوسط (Medium)
* **معيار CVSS v3.1:** `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:N/A:N` (الدرجة: 7.5)
* **رمز الثغرة المصنعي:** CWE-200: Information Exposure / OWASP A05:2021
* **الهدف المتأثر:** `http://example.com/server-status`

#### الملخص التنفيذي (Executive Summary)
أثناء تقييم خوادم الويب المحيطية للشركة، تبين أن واجهة تشخيص خادم أباتشي (`mod_status`) متاحة للعامة عبر المسار `/server-status` دون أي مصادقة أو تقييد للعناوين. تكشف هذه الواجهة بيانات حية شديدة الحساسية تتضمن عناوين IP للمستخدمين المتصلين، ومسارات الطلبات الجارية، ومعلومات البنية التحتية للخادم.

#### الوصف الفني وخطوات التحقق (PoC)
1. إرسال طلب HTTP GET عادي للمسار التشخيصي:
   ```bash
   curl -s http://example.com/server-status
   ```
2. يستجيب الخادم بكود `200 OK` عارضاً لوحة النشاط الكاملة:
   ```html
   <h1>Apache Server Status for example.com</h1>
   <p>Server Version: Apache/2.4.41 (Ubuntu)</p>
   <table>
     <tr><th>PID</th><th>Client</th><th>Request</th></tr>
     <tr><td>1482</td><td>203.0.113.4</td><td>GET /api/v1/auth?token=9f8a7b6c HTTP/1.1</td></tr>
   </table>
   ```
3. لوحظ أن اللوحة تعرض طلبات حقيقية للمستخدمين تتضمن توكنات أمنية صريحة في الروابط.

#### الأثر على الأعمال (Business Impact)
يتيح كشف هذه البيانات للمهاجمين رصد سلوك المستخدمين وسرقة جلساتهم النشطة، واستكشاف العناوين الداخلية للشبكة، مما يعرض الشركة لخرق تشريعي صريح لمتطلبات حماية البيانات (المادة 32 من اللائحة العامة لحماية البيانات GDPR).

#### التوصيات وخطوات الترقيع (Remediation)
يجب تقييد الوصول لمسار `/server-status` وحصره على العناوين المحلية (Localhost) أو شبكات الإدارة الموثوقة فقط:
* في ملف الإعداد `/etc/apache2/mods-available/status.conf`:
  ```apache
  <Location /server-status>
      SetHandler server-status
      Require local
  </Location>
  ```
* مراجعة ملفات إعداد المضيفين الافتراضيين للتأكد من عدم وجود توجيه `Require all granted` عام يلغي هذا التقييد.
```

## 🛡️ 3. دليل الدفاع والتأمين الشامل للخوادم (Production Hardening)

### 1. تأمين خادم إنجنكس Nginx (`/etc/nginx/conf.d/security.conf`)
```nginx
# 1. إخفاء رقم إصدار السيرفر
server_tokens off;

# 2. فرض ترويسات الأمان الدفاعية
add_header X-Frame-Options "SAMEORIGIN" always;
add_header X-Content-Type-Options "nosniff" always;
add_header X-XSS-Protection "1; mode=block" always;
add_header Content-Security-Policy "default-src 'self'; frame-ancestors 'self';" always;
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
add_header Referrer-Policy "strict-origin-when-cross-origin" always;

# 3. حظر تحميل كافة ملفات النقطة والمستودعات (.env, .git)
location ~ /\. {
    deny all;
    access_log off;
    log_not_found off;
}
```

### 2. تأمين تطبيقات Node.js / Express عبر حزمة Helmet
```javascript
const express = require('express');
const helmet = require('helmet');
const app = express();

// تفعيل حزمة Helmet لحقن أكثر من 15 ترويسة أمان وحذف X-Powered-By تلقائياً
app.use(helmet());

// التأكد من العمل في وضع الإنتاج
if (process.env.NODE_ENV !== 'production') {
    console.warn("تحذير: التطبيق يعمل في وضع غير إنتاجي!");
}
```

### 3. تأمين خادم أباتشي Apache (`/etc/apache2/conf-available/security.conf`)
```apache
# إخفاء هوية وتفاصيل نظام التشغيل في أباتشي
ServerTokens Prod
ServerSignature Off

# تعطيل فهرسة المجلدات على مستوى السيرفر بالكامل
<Directory /var/www/>
    Options -Indexes
    AllowOverride None
    Require all granted
</Directory>
```

## 💼 4. أسئلة المقابلات الوظيفية وكيف تجيب عليها باحترافية

#### س 1: "لماذا بدأت الصناعة تستبدل هيدر `X-Frame-Options`، وما هو البديل الحديث له؟"
* **الإجابة النموذجية:** "يتم استبدال `X-Frame-Options` بتوجيه `frame-ancestors` ضمن سياسة أمان المحتوى (**Content Security Policy - CSP**). السبب أن `X-Frame-Options` يتيح خيارات محدودة جداً (`DENY` لمنع التضمين كلياً، أو `SAMEORIGIN` للسماح بنفس النطاق فقط)، ولا يدعم تحديد نطاقات فرعية أو شركاء خارجيين موثوقين. في المقابل، يتيح توجيه `frame-ancestors` في الـ CSP تحديد قوائم بيضاء دقيقة بالنطاقات المسموح لها بتضمين الصفحة. ومع ذلك، في بيئات الإنتاج الحالية نوصي بوضع كِلا الهيدرين معاً لضمان حماية المتصفحات القديمة والحديثة في آن واحد."

#### س 2: "ما الفرق في السلوك الافتراضي بين Apache و Nginx بخصوص فهرسة المجلدات (Directory Listing)؟"
* **الإجابة النموذجية:** "في خادم أباتشي، ميزة الفهرسة تكون مفعلة افتراضياً في معظم توزيعات لينكس عبر خيار `Options Indexes`؛ فإذا دخل المستخدم مجلداً لا يحتوي على ملف `index.html`، يقوم أباتشي تلقائياً برسم شجرة الملفات ما لم يعطلها المدير صراحة بـ `Options -Indexes`. في المقابل، خادم إنجنكس Nginx **يعطل الفهرسة افتراضياً وبشكل قاطع**، ولا يمكن أن يعرض قائمة الملفات إلا إذا قام المدير بإضافة أمر `autoindex on;` يدوياً داخل إعدادات الـ location."

#### س 3: "لو تطبيق Express مضبوط فيه `NODE_ENV=production`، هل هذا يعني أنه آمن تماماً من تسريب رسائل الأخطاء؟"
* **الإجابة النموذجية:** "لا. ضبط `NODE_ENV=production` يعطل فقط مخرجات الخطأ التلقائية المدمجة في إطار Express الأصلي. لكن في الواقع البرمجي، يقوم المطورون غالباً بكتابة معالج أخطاء مخصص (Custom Error Handler) مثل `app.use((err, req, res, next) => { res.status(500).send(err.stack); })`، وهذا الكود المخصص يطبع الـ Stack Trace كاملاً للمستخدم متجاهلاً قيمة المتغير تماماً ما لم يُبرمج داخله شرط يفحص بيئة التشغيل."
