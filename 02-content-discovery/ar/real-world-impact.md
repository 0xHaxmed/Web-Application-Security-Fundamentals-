## 🌐 1. الواقع العملي وإدارة مساحة الهجوم (Attack Surface Management)

في اختبارات الاختراق المتقدمة وعمليات الفريق الأحمر (Red Teaming) ومسابقات صيد الثغرات (Bug Bounty)، تمثل مرحلة الاستطلاع والاستكشاف (Reconnaissance) **أكثر من 80% من أسباب نجاح المهمة**.

كبار الباحثين الأمنيين لا يضيعون وقتهم في فحص التطبيق الرئيسي الذي خضع لعشرات المراجعات الأمنية، بل يبحثون في أطراف المنظومة: **السيرفرات الفرعية، البيئات التجريبية المنسية (Staging)، الحاويات السحابية، والمستودعات البرمجية المتروكة**.

### سيناريوهات حقيقية من أرض الواقع:

1. **المضيفون الافتراضيون الداخليون (Internal Virtual Hosts):**
   * *السيناريو:* تؤمّن الشركة موقعها الرئيسي `app.company.com` بجدار ناري لتطبيقات الويب (WAF) ومصادقة ثنائية، لكن نفس خادم الويب (Apache أو Nginx) مضبوط لخدمة موقع افتراضي داخلي مثل `internal-admin.company.com` أو `stage.company.com`.
   * *الخطر الحقيقي:* هذا النطاق الافتراضي لا يملك سجلاً في الـ DNS العام، فلا يمكن لجوجل أو الماسحات العادية رؤيته. لكن بمجرد قيام المختبر بتخمين هيدر `Host:`، يستجيب السيرفر ويعرض لوحة تحكم تطويرية داخلية خالية تماماً من المصادقة!

2. **تسريب المفاتيح في تاريخ مستودعات Git (CWE-798 / CWE-312):**
   * *السيناريو:* يرفع المطور ملف `.env` يحتوي على مفتاح AWS السري أو بيانات قاعدة البيانات، وبعد نصف ساعة يكتشف الخطأ فيقوم بحذف الملف في كوميت جديد (`Remove secret .env`).
   * *الخطر الحقيقي:* يقوم المهاجمون عبر برمجيات آلية بمراقبة تدفقات GitHub العامة، وسحب المستودع، وتنفيذ أمر `git log -p` لاستخراج المفتاح السري من الفروقات التاريخية (Commit Diff) في ثوانٍ معدودة، مما يؤدي لاختراق البنية السحابية للشركة بالكامل.

3. **حاويات التخزين السحابي العامة (AWS S3 Bucket Exposure):**
   * *السيناريو:* ضبط حاوية تخزين لملفات الوسائط الخاصة بالشركة مع إعطاء صلاحية القراءة للعامة (`Publicly Accessible`).
   * *الخطر الحقيقي:* تخمين اسم الحاوية عبر خوارزميات التسمية الشائعة (`company-backup`, `company-database`) يتيح تحميل نسخ قواعد البيانات الاحتياطية وملفات العملاء دون مصادقة، مما يعرض الشركة لغرامات تنظيمية طائلة وتشهير إعلامي.

## 📝 2. نموذج تقرير احترافي للعميل (Pentest Report Finding)

إليك الصياغة المهنية المعتمدة لتقديم تقرير حول كشف مضيف افتراضي داخلي غير محمي:

```markdown
### تقرير ثغرة: كشف مضيف افتراضي داخلي (Internal Virtual Host) على خادم خارجي

* **مستوى الخطورة:** عالي (High)
* **معيار CVSS v3.1:** `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:L/A:N` (الدرجة: 8.2)
* **رمز الثغرة المصنعي:** CWE-16: Configuration / CWE-200: Information Exposure
* **الهدف المتأثر:** `http://198.51.100.25/` (المضيف: `internal-stage.acme.thm`)

#### الملخص التنفيذي (Executive Summary)
أثناء مرحلة استطلاع البنية التحتية الخارجية للشركة، تم اكتشاف مضيف افتراضي داخلي غير مسجل في خوادم الـ DNS العامة (`internal-stage.acme.thm`) يعمل على نفس خادم الويب العام ذي العنوان `198.51.100.25`. أتاح هذا المضيف إمكانية الوصول غير المصرح به لبيئة التطوير التجريبية، والتي تسرب بيانات اتصال بقواعد البيانات الداخلية دون الحاجة لأي تسجيل دخول.

#### الوصف الفني وخطوات التحقق (PoC)
1. تنفيذ فحص للمضيفين الافتراضيين عبر أداة Gobuster مع التوجيه المباشر لعنوان الخادم:
   ```bash
   gobuster vhost -u http://198.51.100.25/ \
     --domain acme.thm \
     -w /usr/share/wordlists/SecLists/Discovery/DNS/subdomains-top1million-5000.txt \
     --append-domain --exclude-length 312
   ```
2. استجابت الأداة بنجاح بوجود المضيف الافتراضي `internal-stage.acme.thm` مع كود حالة `200 OK` وحجم استجابة 4,812 بايت:
   ```http
   GET / HTTP/1.1
   Host: internal-stage.acme.thm
   ```
3. بالدخول إلى الرابط وُجدت لوحة تحكم تشخيصية خاصة بالمطورين تكشف سلاسل الاتصال بقواعد البيانات الداخلية.

#### الأثر على الأعمال (Business Impact)
يسمح هذا القصور لأي طرف خارجي باستغلال بيئات التطوير غير المحمية للوصول إلى شبكة الشركة الداخلية، والتنقل أفقياً (Lateral Movement) نحو قواعد البيانات الإنتاجية.

#### التوصيات وخطوات الترقيع (Remediation)
1. **عزل الشبكات (Network Segmentation):** نقل كافة بيئات التطوير والاختبار إلى شبكات افتراضية خاصة (VPC) لا يمكن الوصول إليها إلا عبر VPN الشركة.
2. **إعداد المضيف الافتراضي الاحتياطي (Default Catch-All):** تهيئة خوادم Apache أو Nginx لإرجاع كود `404` أو رفض الطلب تلقائياً لأي طلب لا يتطابق هيدر `Host` فيه مع النطاق العام المعتمد:
   ```nginx
   # في خادم Nginx
   server {
       listen 80 default_server;
       server_name _;
       return 404;
   }
   ```
```

## 🛡️ 3. دليل الدفاع وتأمين الأنظمة (Defensive Hardening)

| تقنية الاستكشاف | ما الذي يبحث عنه المهاجم؟ | طريقة التأمين في بيئة العمل الحقيقية |
|---|---|---|
| **`robots.txt`** | مسارات الإدارة الحساسة | **المصادقة قبل التوجيه:** لا تعتمد على الملف للحماية؛ ضع مسارات الإدارة خلف أنظمة مصادقة مركزية (SSO/MFA) واجعل الخادم يطلب كود `401` فوراً. |
| **مستودعات Git** | المفاتيح المسربة في الـ History | **الفحص الآلي للأسرار:** دمج أدوات مثل `Gitleaks` أو `Trufflehog` داخل خطوط أنابيب الـ CI/CD لمنع قبول أي Commit يحتوي مفاتيح API أو كلمات سر. |
| **فحص المضيفين الافتراضيين** | هيدرز الـ Host غير المحمية | **إسقاط الطلبات المجهولة:** ضبط خادم الويب لرفض أي طلب لا يطابق النطاق الرسمي المسجل (Reject Unknown Host Headers). |
| **التخمين الآلي العنيف** | فحص المسارات عبر Gobuster | **جدران حماية الويب WAF وتحديد المعدل:** تفعيل قواعد تمنع الآي بي الذي يصدر أكثر من 50 طلباً في الثانية بنسب أخطاء 404 عالية. |
| **حاويات AWS S3** | أسماء الحاويات التخمينية للشركة | **تفعيل خيار S3 Block Public Access:** حظر الوصول العام على مستوى حساب AWS بالكامل وفرض المصادقة عبر أدوار IAM فقط. |

## 💼 4. أسئلة المقابلات الوظيفية وكيف تجيب عليها باحترافية

#### س 1: "لماذا قد ينجح فحص الـ Virtual Host في اكتشاف موقع ما، بينما يفشل فحص الـ Subdomain DNS تماماً لنفس الموقع؟"
* **الإجابة النموذجية:** "لأن فحص النطاقات الفرعية (`gobuster dns`) يعتمد على خوادم أسماء النطاقات (DNS Servers)؛ فإذا لم تكن الشركة قد أنشأت سجل A Record عام لهذا النطاق، فلن تجده الأداة إطلاقاً. في المقابل، فحص المضيفين الافتراضيين (`gobuster vhost`) يرسل طلبات HTTP مباشرة لعنوان IP خادم الويب نفسه مع تغيير قيمة ترويسة `Host:`، مما يجبر خادم الويب (مثل أباتشي أو إنجنكس) على مطابقة القيمة بجدول التوجيه الداخلي لديه، حتى لو لم يكن هناك أي سجل DNS مسجل له."

#### س 2: "إذا قام مطور برفع كلمة مرور في مستودع GitHub خاص، ثم حذفها بعد دقيقة في Commit جديد، هل زال الخطر؟"
* **الإجابة النموذجية:** "قطعاً لا. نظام Git مبني على شجرة تاريخية غير قابلة للتغيير العادي؛ والبيانات تظل محفوظة بالكامل في تاريخ الـ Commits السابقة ويمكن لأي شخص يملك وصولاً للمستودع استخراجها بسهولة. أمنياً، بمجرد رفع أي اعتماد (Credential) إلى مستودع، يجب اعتباره مخترقاً ومكشوفاً فوراً، وتغييره وتدويره (Rotate & Revoke) على الفور في السيرفر أو المزود، ثم تنظيف تاريخ الـ Git بأداة متخصصة مثل `git-filter-repo`."

#### س 3: "كيف تتعامل مع خادم DNS يقوم بتفعيل سجل الـ Wildcard أثناء فحص النطاقات الفرعية؟"
* **الإجابة النموذجية:** "سجل الـ Wildcard (`*.domain.com`) يقوم بإرجاع عنوان IP صالح لأي استعلام حتى لو كان النطاق الفرعي عشوائياً وغير موجود، مما يجعل الأدوات تولد آلاف النتائج الإيجابية الزائفة (False Positives). الحل هو استخدام راية `--wildcard` في أداة Gobuster؛ حيث تقوم الأداة بإرسال استعلامات لنطاقات عشوائية مستحيلة الوجود لتسجيل عنوان الـ IP الأساسي للـ Wildcard، ثم تستبعد تلقائياً أي نتيجة تطابق هذا العنوان من مخرجات الفحص النهائي."
